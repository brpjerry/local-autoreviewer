One thread per finding, and long reviews that stay readable.

- **One inline comment per finding or nit:** every edit inside the PR's diff used to get a comment of its own, so a fix spread over several places opened several threads. 73 of 201 findings were split like that. The author's agent then pasted the same reply into each thread, four times on coversync#8. Now each finding or nit with an applicable edit inside the diff gets one comment. Its first such edit is the one-click suggestion, and the rest of the fix is shown in the same comment as collapsed diffs, since a suggestion can only replace its own comment's lines. The review body still shows every edit. No commit made with GitHub's "Commit suggestion" button appears in the history of the reviewed PRs, so little is lost by fewer one-click suggestions. A comment whose extra diffs would make it too long for GitHub points to the review instead.
- **Long reviews:** a review over GitHub's size limit used to drop its nits and then cut the text at a fixed length, which could land inside a diff or a collapsed block and garble everything after it. Now every proposed change is first shortened to 80 lines and 4,000 characters in the body. An inline suggestion still has its edit whole. Only then are the nits left out. As a last resort the body is cut before the first finding, heading or list item that doesn't fit, and never at a line that a reviewer wrote. This was deferred from the review of 0.5.0.
- **Review data:** an edit's `inline` flag now marks the one edit per item that was a one-click suggestion.
