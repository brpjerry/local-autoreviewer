Later pushes to a PR get follow-up reviews that check the previous round's findings, proposed fixes land on the right lines, and reviewers are asked to find everything in their first pass.

- **Follow-up reviews:**
  - After a PR's first review, each later push gets a follow-up instead of a full review.
  - Each agent checks every open finding from the previous round, both agents' findings included, and marks it fixed, partly fixed, not fixed or obsolete.
  - It also reports regressions in what changed since, and nothing else.
  - Base commits merged into the PR don't count as its changes.
  - Findings you triaged as declined, false positive, duplicate or deferred aren't asked about again.
  - A stacked PR keeps its follow-ups when the PR below it merges and it is retargeted, even after a squash merge, as long as the old base's changes are all in the new one.
  - It's a full review again when:
    - the PR is retargeted to a base without the old base's changes;
    - the previous commit is gone from the mirror;
    - a conflicting merge mixes the PR's changes with its base's;
    - the changes since the last review are over the size limits.
- **Proposed changes are anchored** by the text they replace:
  - Each edit carries the lines it means to change.
  - An edit whose line numbers are off is moved to where that text is: the nearest copy within 30 lines, or the only copy in the file.
  - An edit whose text can't be placed is left out of the review, with a note, instead of being suggested on the wrong lines.
  - How each edit was placed is recorded in the review data.
- **One systematic pass:** the review prompt asks for a single thorough pass over inputs, order of operations, concurrency, failure part-way, whether tests test what they should, and the reviewer's own proposed edits. On replays of earlier PRs this raised the share of all eventually-found issues reported in round one from about 43% to about 75%.
- **Developer tools:**
  - `tools/live` runs the service from a git worktree instead of the package, so a change can be tried without a release.
  - `tools/replay` replays a past commit through the real pipeline with other prompts, without posting.
  - Both can hold off the worker's new reviews while they deploy or replay (files in `holds/` under the state directory). The worker checks holds inside the transaction that claims a review, so a review it was about to start either waits or is counted as running.

0.1.1 was never published, so this release also includes its changes:
- calibrated severity, with impact, likelihood and trigger;
- severity modifiers for fixes that remove lines or read worse;
- one-click suggested changes;
- review data with `triage` and `findings --json`;
- `review` owning its jobs;
- post retries without re-running the agent;
- polling without holding the write lock;
- `--version`.
