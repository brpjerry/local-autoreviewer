Reviewers raise fewer findings that authors decline.

The prompt changes come from a second read of the review feedback authors left. Most declined findings were problems rated too likely, problems the PR didn't cause, or consequences of a decision the author had already made. Fix size mattered less.

**Full reviews** (and follow-ups that review the whole PR):
- **Likelihood:** input that no common tool or normal workflow produces, or a setup the project doesn't support, is `rare`. A trigger that needs unusual input says what produces it.
- **Stakes and role:** a wrong value on screen that the next refresh corrects costs less than data written wrong or lost. A failure in a test helper, a development tool or an example costs its developers, not the project's users.
- **Pre-existing problems:** reviewers check in pr.diff that the PR's own lines cause a problem. One the base branch already had, which the PR only makes reachable another way, is labelled as predating the PR, and only what the PR adds is rated.
- **Decisions are not claims:** what the project's docs, code comments, the description or commit messages declare out of scope, unsupported or deliberate is the author's call. Reviewers don't report what follows from it as a finding, and may ask about it once in `questions`. Claims about the code are still checked, now including what was tested and why the design was chosen.
- **Shared causes:** problems with one cause are reported once, listing where it shows up, with whether narrowing what the code supports would be simpler. Reviewers search the PR for the same pattern elsewhere.
- **Sized fixes:** a minor finding's fix should take a few lines; a bigger one says so, and whether documenting the limitation would do. Reviewers check whether the code already fails safely before adding a guard, say what a fix adds to a common path and lead with a cheaper one, and check that the normal case still works.
- **Test gaps:** if none of the project's existing kinds of test can reach the behaviour, the gap says so in one line and suggests moving the logic where a test can call it, or names the manual check. No tests of what a library, the database or the language guarantees. A proposed CI check must pass on the base branch.
- **Questions:** for what only the author can answer. A failure the reviewer can trace in the code is a finding. A question about a library checks the pinned version first.

**Follow-ups:**
- A declined finding gets one line with the author's reason. The follow-up contests it only with something the reason doesn't cover (an input or path the author didn't consider, or a cheaper fix), and doesn't restate it or rate it higher.
- A fix the author agreed to make only in part is judged against that part.
- A regression must come from the new commits' lines; a problem already there at the previous commit isn't one.
- What the author declared out of scope isn't reported as a regression.
- The summary says whether what's still open justifies another round of fixes.
