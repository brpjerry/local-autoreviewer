The review prompts now steer away from the kinds of finding authors declined most.

The prompt changes come from a second read of the review feedback authors left. Most declined findings were problems rated too likely, problems the PR didn't cause, or consequences of a decision the author had already made. Fix size mattered less.

**Full reviews** (and follow-ups that review the whole PR):
- **Likelihood:** input that no common tool or normal workflow produces by accident, or a setup the project doesn't support, is `rare`. Input an untrusted party controls is rated by who can send it. A trigger that needs unusual input says what produces it.
- **Stakes and role:** a wrong value on screen that the next refresh corrects costs less than data written wrong or lost. A failure that stays in a test helper or an example costs the project's developers, not its users.
- **Pre-existing problems:** reviewers check that the PR causes a problem, by its lines or by what it leaves out (a caller, a version number or a migration it should have updated). One the base branch already had, which the PR only makes reachable another way, is labelled as predating the PR, and only what the PR adds is rated.
- **Declared limits:** what the project's docs, code comments, the description or commit messages declare out of scope, unsupported or deliberate is the author's call, and the limit itself isn't reported as a defect. A failure in supported behaviour that can be fixed while keeping the limit still is. A small change that would lift a declared limit is proposed once, as a minor finding that says the limit was declared; other doubts about a decision are asked once in `questions`. Claims about the code are still checked, now including what was tested and why the design was chosen.
- **Whole-PR follow-ups** get the pre-existing and declared-limit rules too: they moved from the ground rules into the method, which those follow-ups use.
- **Shared causes:** problems with one cause are reported once, listing where it shows up, with whether narrowing what the code supports would be simpler. Reviewers search the PR for the same pattern elsewhere.
- **Sized fixes:** for a minor finding, above all a rare one, reviewers propose the smallest change that keeps the failure safe or visible (refuse the input, report the error, or document the limitation) rather than full support for the case. A fix that still needs more than a few lines says so first. Reviewers check whether the code already fails safely before adding a guard, say what a fix adds to a common path and lead with a cheaper one, and check that the normal case still works.
- **Test gaps:** if none of the project's existing kinds of test can reach the behaviour, the gap says so in one line and suggests moving the logic where a test can call it, or names the manual check. No tests of what a library, the database or the language guarantees. A proposed CI check mustn't fail on the base branch for an unrelated reason.
- **Questions:** for what only the author can answer. A failure the reviewer can trace in the code is a finding. A question about a library checks the pinned version first.

**Follow-ups:**
- A declined finding gets one line with the author's reason. The follow-up contests it only with something the reason doesn't cover (an input or path the author didn't consider, or a cheaper fix), and doesn't restate it or rate it higher.
- A finding the author fixed in part and declined the rest of is `declined`, with what was fixed, so its thread stays open and later rounds see the decision.
- A regression must come from the new commits, by their lines or what they leave out; a problem already there at the previous commit isn't one.
- A limit the author declared isn't reported as a regression; a failure in supported behaviour it doesn't excuse still is.
- The summary says whether what's still open is worth another round of fixes, judged by what it would cost if left.

**Inline Codex reviews** (`mode = "inline"`, no tools) now also get the PR's description and commits and the project's docs, so the claim and declared-limit rules can work there. Each is capped like the follow-up files.
