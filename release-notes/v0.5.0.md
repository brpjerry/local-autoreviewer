Follow-ups review new code in full, and a merged duplicate keeps the other reviewer's fix.

- **New code in a follow-up:** a follow-up used to check the previous findings and look for regressions in the new commits, and nothing else, so a feature added after the first review got only that narrow look. When the changes since the previous review add new code, meaning behaviour none of the previous findings asked for, the follow-up now also reviews the whole PR as if it were new. It uses the full review's method and coverage, and reports test gaps, questions and nits as a review does. It still records each previous finding's status. The post says which reviewers did this, and lists their findings as "New findings". Follow-ups that only fix the previous findings are unchanged.
- **Merged duplicates:** when both reviewers report the same issue, the post keeps one copy, and until now only that copy's proposed fix. On upscale-relay-android#64 this dropped the complete fix: Codex's also reset the fields on reload, while the kept copy cleared them in only one of two places. The other reviewer's fix is now shown under the kept one when it proposes a change the kept one doesn't, with its suggestion and its changes as diffs. It appears in the review body only, so two one-click suggestions never compete for the same lines. In the review data so far, 30 of 32 merged duplicates had proposed edits of their own.
- **Review data:** `jobs.new_code` (migration 7) records whether a follow-up found new code and reviewed the whole PR. `findings --json` includes it. A follow-up's test gaps, questions and nits are recorded like a review's.
