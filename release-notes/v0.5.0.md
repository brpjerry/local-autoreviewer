Follow-ups review new code in full, and a merged duplicate keeps the other reviewer's fix.

- **New code in a follow-up:** a follow-up used to check the previous findings and look for regressions in the new commits, and nothing else, so a feature added after the first review got only that narrow look. When the changes since the previous review add new code, meaning behaviour none of the previous findings asked for, the follow-up now also reviews the whole PR as if it were new. It uses the full review's method and coverage, and reports test gaps, questions and nits as a review does. It still records each previous finding's status. So that it doesn't post things again, it gets `already-raised.json`: the nits, test gaps and questions of the PR's earlier rounds, and the findings you triaged away, with your decision and note. The post says which reviewers did this, and lists their findings as "New findings", or as "Regressions and new findings" when only one reviewer reviewed the whole PR. Follow-ups that only fix the previous findings are unchanged, and any test gaps, questions or nits such a follow-up returns are dropped.
- **Merged duplicates:** when both reviewers report the same issue, the post keeps one copy, and until now only that copy's proposed fix. On upscale-relay-android#64 this dropped the complete fix: Codex's also reset the fields on reload, while the kept copy cleared them in only one of two places. The other reviewer's fix is now shown under the kept one when it proposes a change the kept one doesn't, with its suggestion and its changes as diffs. It appears in the review body only, so two one-click suggestions never compete for the same lines. A fix that matches the kept one, or an alternative already shown, apart from trailing whitespace, isn't repeated. In the review data so far, 30 of 32 merged duplicates had proposed edits of their own.
- **Proposed changes shown in full:** the review body cut each proposed change at 80 lines, because its inline suggestion had it whole. A change that isn't an inline suggestion (an alternative fix, or an edit outside the PR's diff) had no other copy, so an edit that replaced 81 lines showed none of its replacement. Such changes are now shown in full. GitHub's limit on the body still applies.
- **Review data:** `jobs.new_code` (migration 7) records whether a follow-up found new code and reviewed the whole PR. `findings --json` includes it. A follow-up's test gaps, questions and nits are recorded like a review's.
